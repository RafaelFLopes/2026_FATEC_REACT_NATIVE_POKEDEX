ETAPA 03Análise de Componentização
O que foi bem feito
  • Pattern platform-specific (ios/android/web) aplicado corretamente em Alert, Button, NavBar, PokemonCard, PokemonList, TeamSlot
  • PokemonCard e PokemonList bem encapsulados — toda a lógica de listagem está nos componentes
  • TeamSlot gerencia seus próprios estados visuais (empty, filled, swapMode)
  • Pokeball/SpinningPokeball seguem o princípio de composição corretamente
  • Alert com sistema semântico de cores bem definido
Problemas encontrados
  • Icon existe mas ninguém o usa — NavBar define ícones SVG diretamente inline
  • Nenhum hook customizado — lógica de Alert, loading e fetch duplicada em 4 telas
  • Não existe PageHeader — header com logo e fundo é repetido em Dashboard e Profile
  • PokemonMascot está acoplado a Pikachu (hardcoded URL). Nome sugere reusabilidade inexistente
  • StatCard não tem types.ts separado, inconsistente com os demais componentes
  • Button não expõe textStyle — cor do texto não é customizável
Componentes faltando que deveriam existir:
useAlert (hook)
A lógica de alertData + isAlertVisible + showAlert() é copiada em Login, Register, Dashboard e Team — quatro arquivos. Um hook customizado eliminaria essa duplicação completamente. 
// Deveria existir em src/hooks/useAlert.ts
function useAlert() {
  const [visible, setVisible] = useState(false);
  const [data, setData] = useState({...});
  function show(title, message, type) {...}
  return { visible, data, show, hide };
}
PageHeader (componente)
O header com logo Pokémon (fundo #12122A, borda inferior, logo centralizado) aparece identicamente em dashboard.tsx e profile.tsx. Deveria ser um componente PageHeader com slot opcional para conteúdo direito (como o contador de capturados).
LoadingScreen (componente)
O padrão loading ? ActivityIndicator : conteúdo aparece em Dashboard, Team e Profile com o mesmo visual. Um componente LoadingOverlay ou um hook useLoading centralizaria isso.

ETAPA 05Boas Práticas de Engenharia de Software
SOLID
4.5/10
SRP (Single Responsibility): Telas acumulam UI + estado + lógica de negócio + chamadas API + estado de alert. Dashboard.tsx faz fetch de dados, normalização de IDs, lógica de captura e gerenciamento de UI.

OCP (Open/Closed): Para adicionar novo tipo de pokémon seria necessário editar colors.ts — aceitável. Para adicionar nova tela autenticada é simples. Razoável.

DIP (Dependency Inversion): Telas dependem diretamente das funções de integração. Não existe interface ou abstração intermediária. Se a API mudar, múltiplas telas precisam ser alteradas.
Clean Code
6.0/10
Nomes de variáveis e funções são claros e descritivos (handleCapture, handleSlotSwap, toNumericId). Funções pequenas e com única responsabilidade.

Problemas: Magic strings de cor em todo o código ('#E53935', '#0D0D1F', '#12122A') quando existe um sistema de cores importável. Estado de alert duplicado 4 vezes. Estilo hint declarado mas nunca usado em 2 arquivos.
Componentização
6.5/10
O conjunto de componentes cobre bem o necessário. A abordagem platform-specific é madura e correta. PokemonCard e TeamSlot são bem projetados.

Pontos que derrubam a nota: Icon component sem uso nenhum. Ausência de PageHeader e LoadingOverlay (padrões visuais repetidos). Ausência completa de custom hooks — lógica repetida deveria estar em src/hooks/.
Reutilização de Código
4.5/10
Este é o maior ponto fraco do projeto. Três pares de arquivos mobile/web duplicam 90%+ do código incluindo toda a lógica de negócio. O padrão de alert é copiado em 4 telas. O header visual é copiado em 2 telas. A função toNumericId é definida inline em team.tsx quando poderia ser um utilitário compartilhado.
Organização de Pastas
7.0/10
A estrutura app/, components/, context/, integration/, constants/ está bem organizada e segue convenções do Expo Router.

Faltando: src/hooks/ para hooks customizados. src/utils/ para funções utilitárias como toNumericId. A nomenclatura "integration" é incomum — "services" ou "api" seria mais reconhecível pela comunidade.
Escalabilidade
5.5/10
A abordagem platform-specific (.ios/.android/.web) escala bem para adicionar suporte a novas plataformas. O sistema de cores por tipo de pokémon é extensível. A separação em integration files está boa.

Problemas: Adicionar uma nova tela exige reimplementar o padrão alert + loading do zero. A duplicação mobile/web cresce linearmente com novas telas. Sem hooks, sem repositório — difícil adicionar cache ou offline.
Manutenibilidade
5.0/10
A duplicação é o inimigo principal da manutenibilidade. Corrigir o bug do botão "SALVAR" no perfil requer editar 2 arquivos. Uma mudança no fluxo de login precisa ser feita em 2 arquivos. O token JWT não está sendo enviado — se alguém quisesse corrigir, teria que atualizar múltiplos pontos.
Legibilidade
7.0/10
Nomes de variáveis, funções e componentes são claros. A consistência do idioma (PT-BR para nomes de domínio como nome, vitorias) é mantida. O uso de SCREAMING_SNAKE_CASE para constantes como MAX_TEAM é correto. Arquivos bem formatados.

Ponto negativo: Strings de cor sem semântica ('#E53935' em vez de Colors.accent / Colors.semantic.error.text).
ETAPA 06Visão do Professor Avaliador
1️⃣
A separação entre telas e componentes foi feita corretamente?
Parcialmente. Os componentes visuais estão bem separados — Button, Card, Input, Alert, PokemonCard, TeamSlot estão em seus próprios módulos e são usados pelas telas. O problema está na lógica de negócio dentro das telas: handleCapture, handleSlotSwap, loadStats — toda essa lógica de domínio deveria estar em custom hooks (useDashboard, useTeamManager, useProfile), deixando as telas como camadas puramente de composição visual.
2️⃣
Existem componentes desnecessários?
Sim. O componente Icon foi criado mas nunca é utilizado em nenhuma parte do projeto. O NavBar define seus próprios ícones SVG inline em vez de usar o Icon. É um componente morto que ocupa espaço sem valor.
3️⃣
Existem componentes faltando?
Sim, três claramente: PageHeader (header com logo repetido em 2 telas), LoadingOverlay ou padrão de loading consistente, e principalmente useAlert como custom hook — o padrão de alert está copiado em 4 telas.
4️⃣
Existe reutilização adequada?
A reutilização de componentes visuais é boa. A reutilização de lógica é insuficiente. O maior problema é a duplicação das telas mobile/web (Login, Register, Profile) que copiam toda a lógica de negócio. Um professor focado em arquitetura vai identificar isso imediatamente como violação do DRY.
5️⃣
O projeto parece profissional?
Visualmente sim — a UI tem identidade visual coerente, animações cuidadosas, sistema de cores por tipo de pokémon, e suporte multi-plataforma. Isso impressiona à primeira vista. Mas sob o capô, a duplicação de código, o bug do botão SALVAR que não salva nada, e a ausência de custom hooks mostram imaturidade arquitetural.
6️⃣
O que mais chamaria atenção NEGATIVAMENTE?
1. O botão "SALVAR" no perfil não salva nada. Isso é uma feature incompleta — o modo de edição existe na tela mas a alteração nunca é persistida.

2. A duplicação dos arquivos .web.tsx com toda a lógica de negócio copiada. Um professor de Engenharia de Software vai abrir index.tsx e index.web.tsx lado a lado e ver 90% do código idêntico — isso é textbook DRY violation.

3. O componente Icon existe mas não é usado — e o NavBar redefine ícones inline. Mostra falta de coesão no design do sistema.
7️⃣
O que mais chamaria atenção POSITIVAMENTE?
1. A estratégia platform-specific — usar index.ios.tsx, index.android.tsx, index.web.tsx para Alert, Button, NavBar, PokemonCard demonstra conhecimento avançado de React Native. Poucos alunos fazem isso.

2. O AuthContext está bem implementado com persistência via AsyncStorage, cleanup correto no signOut, e carregamento de dados iniciais no useEffect.

3. A qualidade visual — sistema de cores por tipo de pokémon, animações suaves, dark theme consistente.
ETAPA 07Erros Críticos
🔴 GRAVES
🔴 Botão SALVAR no perfil não persiste dados
Arquivo: src/app/(app)/profile.tsx · Linha 89  |  Repetido em profile.web.tsx · Linha 77
O botão "SALVAR" chama apenas setEditMode(false). A função updateStats() está exportada em authIntegration.ts e nunca é chamada. O usuário pode editar seu nome na tela, clicar em SALVAR, e a alteração se perde ao recarregar o app. É uma feature que parece funcionar mas não funciona.
Correção: Chamar updateStats(userId, { level: nivel, vitorias, derrotas }) (ou o endpoint correto para nome) antes de setEditMode(false). Adicionar estado de loading durante o save e exibir Alert de sucesso/erro.
🔴 Token JWT não enviado nas requisições autenticadas
Arquivos: src/integration/teamIntegration.ts · src/integration/authIntegration.ts
O AuthContext armazena o token retornado pelo login, mas nenhum dos arquivos de integração envia o token no header Authorization: Bearer <token>. As chamadas para /pokemon/v1/team, /pokemon/v1/captured e /auth/v1/stats vão sem autenticação. Se a API não valida o token server-side, qualquer userId poderia acessar dados de outros usuários.
Correção: Criar um interceptor Axios que leia o token do AuthContext ou AsyncStorage e adicione ao header de toda requisição autenticada. Alternativamente, passar o token como parâmetro para as funções de integração.
🔴 Duplicação de lógica de negócio entre arquivos mobile e web
index.tsx vs index.web.tsx · register.tsx vs register.web.tsx · profile.tsx vs profile.web.tsx
Os três pares de arquivos copiam ~90% do código, incluindo toda a lógica de negócio: handleLogin, handleRegister, loadStats, declaração de estados, handlers de alert. A única diferença real é o layout (ScrollView vs View centralizada, maxWidth, tamanho de pokéball). Isso viola diretamente o princípio DRY e cria 3 pontos duplicados de manutenção.
Correção: Extrair toda a lógica para hooks customizados (useLoginForm, useRegisterForm, useProfileData). Os arquivos .tsx ficam apenas com o layout. Lógica em um lugar só.
🟠 MÉDIOS
🟠 Padrão de Alert duplicado em 4 telas
index.tsx · register.tsx · dashboard.tsx · team.tsx
Os estados alertData + isAlertVisible e a função showAlert() são copiados com variações mínimas em 4 telas diferentes. Qualquer alteração no comportamento padrão do alert precisa ser feita em 4 lugares.
Correção: Criar src/hooks/useAlert.ts que encapsula esse padrão e retorna { visible, data, show, hide }.
🟠 Componente Icon criado porém completamente ignorado
src/components/icon/index.tsx
O componente Icon foi desenvolvido para ser um wrapper de ícones SVG reutilizável, mas o NavBar — o único lugar com ícones SVG no app — define seus próprios componentes PokedexIcon, TeamIcon e ProfileIcon inline. O Icon não é importado em lugar algum.
Correção: Usar o Icon no NavBar (ou remover o componente se não for usar). Manter código morto cria confusão.
🟠 Sistema de Cores ignorado na maioria dos arquivos
Praticamente todas as telas e componentes
O arquivo constants/colors.ts foi criado com Colors (cores semânticas) e getColor() (cores por tipo), mas apenas dois arquivos o utilizam: alert/index.web.tsx e pokemon-card/styles.ts. Todas as telas usam strings hex hardcoded — '#0D0D1F', '#E53935', '#12122A', '#9090B0' — que poderiam ser constantes do Colors.
Correção: Adicionar as cores do tema escuro ao Colors (Colors.bgPrimary, Colors.bgSurface, Colors.bgBorder, Colors.accentRed) e substituir as strings hardcoded.
🟠 URL de imagem do PokemonMascot hardcoded no código
src/components/pokemon-mascot/index.tsx · Linha 33
A URL https://raw.githubusercontent.com/PokeAPI/sprites/master/... está hardcoded no componente. Se o CDN ficar indisponível, a tela de login fica sem imagem. Além disso, o componente se chama "PokemonMascot" mas é hardcoded para Pikachu — não é reaproveitável para outro pokémon.
Correção: Passar a URL ou o ID do pokémon como prop, ou importar a imagem localmente como asset.
🟡 LEVES
🟡 react-native-reanimated instalado mas não utilizado
package.json
A biblioteca de animações mais pesada do RN está no package.json, mas todas as animações usam o Animated built-in do React Native. Dependência desnecessária aumenta o bundle.
🟡 Estilo hint declarado mas nunca referenciado no JSX
src/app/(auth)/index.tsx · src/app/(auth)/index.web.tsx
O StyleSheet define hint nos dois arquivos de login, mas nenhum elemento usa style={styles.hint}. Código morto.
🟡 updateStats exportada mas nunca chamada
src/integration/authIntegration.ts · Linha 29
Função exportada sem consumidores no projeto. Dead code de API — relacionado ao bug do botão SALVAR.
🟡 any em pokemonIntegration.ts
src/integration/pokemonIntegration.ts · Linhas 22–23
(t: any) e (s: any) no mapeamento de tipos e stats da PokeAPI. TypeScript configurado em strict mode mas o benefício é perdido nesse ponto.
🟡 Button não expõe prop para customizar cor do texto
src/components/button/index.ios.tsx
O título do botão está sempre em '#fff'. Impossível criar um botão com texto escuro (ex: botão em fundo amarelo) sem modificar o componente.
🟡 StatCard sem arquivo types.ts separado
src/components/stat-card/index.tsx
Todos os outros componentes têm types.ts separado. StatCard define StatCardProps inline no próprio index.tsx — inconsistência com o padrão adotado.
